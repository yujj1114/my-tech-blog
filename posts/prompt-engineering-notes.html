从 Prompt 到 Prompt Engineering：我踩过的几个坑

2026年11月11日·约 7 分钟#AI#Prompt#实践

我做过一个很无聊但很有用的实验：让模型把用户反馈提炼成结构化标签。同一个任务，我从第 1 版改到第 7 版，把每一版的输出都存了下来。回头看，这就是一部浓缩的 Prompt Engineering 进化史。

第 1 版：「帮我总结反馈」

输出随缘：有时是一段话，有时是要点列表，有时自作主张加一堆建议。问题不在模型，在于我什么都没约束——「总结」这两个字，人和模型的理解差着十万八千里。

第 2~4 版：把要求一条条加上去

加了角色（「你是一位产品经理」）、加了输出格式（「只返回 JSON」）、加了字段说明。每一版都解决一个具体问题，稳定度肉眼可见地上升。但 JSON 还是会偶尔带 markdown 代码块包裹——模型「好心」地帮我格式化了。

第 5 版：两三个示例抵十句描述

与其反复强调「语气要客观」，不如直接塞两条输入→输出的样例。Few-shot 一上，风格漂移基本消失。这是所有版本里性价比最高的一次改动。

第 7 版：像管代码一样管 prompt

最后我给这个 prompt 建了个小文件，带编号、变更记录和测试用例：

# V7 · 反馈标签提取
# 变更：V6 加了 few-shot；V7 收紧 JSON 输出
角色：你是产品经理，只做分类，不给建议。
输入：<用户反馈原文>
输出：纯 JSON，不要 markdown 代码块，字段：
  {"tags": ["标签"], "sentiment": "pos|neg|neutral"}
示例：
  输入「太卡了」，输出 {"tags":["性能"],"sentiment":"neg"}

改崩了能一键退回上一版，这比任何「技巧」都重要。

结论

Prompt Engineering 不是玄学，是把意图结构化表达、并像代码一样迭代管理的工程能力。七个版本里没有一个「神级技巧」，全是把模糊变具体的笨功夫。
