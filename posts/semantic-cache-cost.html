语义缓存踩坑记：命中率冲到 62%，我差点把「退款」答成「退货」

读书笔记助手上线后我发现一个浪费：同一个问题，一天内被问了十几次，每次都老老实实调用模型，慢且烧钱。于是我加了语义缓存——不比对字符串是否完全相同，而是比对问题的向量是否足够接近。上线一周，命中率 62%，p95 延迟从 2.3 秒降到 80 毫秒。但中间踩的几个坑，比省下的钱更值得记。

第一版：先用精确缓存探路

我最早只做了精确匹配：把用户输入原样做 MD5 当 key。命中率只有 19%，因为用户几乎不会一字不差地重复提问。语义缓存的思路是把问题向量化，在缓存库里找余弦相似度最高的一条，超过阈值就复用答案。

def cached_answer(q, threshold=0.95):
    qv = embed(q)                      # 和问题库同一个 embedding 模型
    hit = cache.search(qv, top_k=1)
    if hit and hit.score >= threshold:
        metrics.inc("cache_hit")
        return hit.answer
    ans = llm.answer(q)
    cache.add(qv, q, ans, version=PROMPT_VER)
    return ans

坑一：阈值 0.85 把「退款」和「退货」合并了

我一开始把阈值设成 0.85，命中率漂亮地冲到 78%。直到有用户问「怎么退款」，系统返回了「请寄回商品」——缓存里躺着的是「怎么退货」的答案。这两句话嵌入后相似度 0.88，但业务意图完全相反。我把阈值提到 0.95，命中率回落到 62%，但这类错误消失了。缓存的代价不是少命中几次，而是答错一次的可信度损失。

坑二：缓存 key 没带 prompt 版本号

更隐蔽的一次：我改了 prompt 的输出格式，用户却持续拿到旧格式答案。排查半天才发现缓存里存的是上一次 prompt 生成的结果，而 key 只有问题本身。加上版本号后，prompt 一变缓存自动失效——我把这个字段写进 key，而不是等它慢慢过期。

坑三：时效性内容根本不该缓存

有用户问「今天有多少新文件」，缓存把上午的答案给了下午的人。我给缓存加了一层白名单：只有静态知识类问题（概念解释、操作说明）才进缓存，涉及「今天、最新、当前」的问题直接跳过。规则很土，但比一刀切靠谱。

成本账与结论

一周内总共 1840 次问答，命中 1141 次，省下约 26 万 token，按当前价格大概 ¥3.9——数字不大，但 p95 延迟从 2300ms 降到 80ms，体感提升比省钱更明显。结论：语义缓存是延迟优化手段，顺便省钱；阈值宁高勿低，key 一定带版本，时效内容直接放行。缓存命中的是「答案可复用」这个判断，而判断错了，比不缓存更贵。
