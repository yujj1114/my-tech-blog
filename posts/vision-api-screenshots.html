把 NPI 的报错截图丢给视觉模型：我从 413 错误一路调到了可用

我在 NPI 系统里排查问题，经常要对着同事发来的报错截图眯着眼找错误码——字小、压缩糊、还要来回放大。于是我想做个小工具：把截图丢给视觉模型，直接让它读出错误码并解释原因。听起来是「传张图 + 问一句」的十分钟活，实际调了两天。

第一个坑：413 请求体过大

我直接把一张 1920x1080 的截图读成 base64 塞进请求，第一次调用就返回 413 Request Entity Too Large——原图 4.8MB，base64 编码后膨胀约 33%，超过网关 6MB 的限制。先做有损压缩并限制长边到 1568 像素，体积降到 340KB，请求才通。

from PIL import Image
import io, base64

img = Image.open(path).convert("RGB")
img.thumbnail((1568, 1568))          # 长边限制
buf = io.BytesIO()
img.save(buf, format="JPEG", quality=82, optimize=True)
b64 = base64.b64encode(buf.getvalue()).decode()
# data URL: "data:image/jpeg;base64," + b64

第二个坑：detail=low 省 token，但看不清小字

视觉 API 的 detail 参数直接影响计费：low 固定约 85 tokens，high 按图块算，1568x1080 的图约 1105 tokens。我为了省钱全用 low，结果模型把错误码 NO_2026 读成了 N0_2026——字母 O 和数字 0 在压缩后的小字里糊成一团。这个错误很致命：按错误码去查文档，查到的完全是另一条。

真正有效的办法：先裁剪再放大

我把策略改成两步：先用 high 让模型定位报错区域的大致坐标，再用 PIL 把那块区域裁出来、放大 3 倍、单独送一次。第二次调用只处理局部，token 反而比整图 high 少，错误码识别准确率从 71% 提到 96%。把「看清」这件事交给预处理，而不是指望模型更强。

一个意外收获：让模型输出结构化结果

最初我让它「告诉我错误码和原因」，输出总是一段话，程序没法用。改成要求返回 JSON：{"code": "...", "reason": "...", "confidence": 0.9}，并给 confidence 设阈值——低于 0.75 就不自动填单，转人工。这样既自动处理了大部分常见报错，又不至于因为一次误读把工单写错。

结论

多模态调用的难点不在 API 本身，而在「送进去之前」：尺寸、压缩、区域裁剪、计费模式，每一步都影响结果。我现在的默认配置是：长边 1568、JPEG quality 82、先 high 定位再局部放大、输出带置信度的结构化结果。两天踩坑换来的这几行配置，比换更强的模型管用得多。
